# Steward 的架构、部署与 Ego 记忆

## 架构思想：用代码连接 S2 推理与 S1 技能

Steward 把任务推理、任务策略和具身执行分开。**S2 负责形成策略，可执行代码承载策略，S1 负责执行技能。** Ego Harness 中的 LLM 根据任务和观测生成、取回或修订程序。程序在 `run_code` 中读取观测，用条件和循环选择技能及其参数。Ego Runtime 执行技能并处理运动反馈，实时控制留在本地。 [Steward 系统设计](../../steward.md)

| 层次 | 职责 | 典型输入与输出 |
|---|---|---|
| **S2 · 任务推理** | 理解目标、选择做法，遇到异常时修订策略 | 任务指令与执行证据 → 新生成或复用的程序 |
| **Code · 任务策略** | 根据观测和任务进度决定下一步调用哪个技能、传入什么参数 | 当前观测与中间结果 → 技能调用 |
| **S1 · 具身技能** | 将一次技能调用落实为动作，在执行中处理本体反馈 | 目标与参数 → 抓取、放置、倾倒等动作及结果 |

**Code as Policies 描述的是中间这层。** 编排代码本身就是任务层 policy。S1 技能内部也可以有自己的动作 policy，用于根据目标和反馈决定如何运动，可以由学习模型、规划器、状态机或控制器实现。两层策略在不同粒度上做决策，前者决定何时抓哪一片，后者负责如何抓住并放稳。 [Code as Policies 原论文](https://arxiv.org/abs/2209.07753) · [翻面执行](../../steward/src/steward/ego/skills.py)

长城拼图展示了这种分工带来的复用。Ego 取回猫拼图任务中保存的 `assemble_picture_from_reference`，用新的盒盖图案和拼片观测运行配方，继续调用底层抓取、翻面和放置技能。配方可以修订并写回能力库，供下一次任务使用。 [拼图复用记录](../../steward.md#13-implementation-progress) · [长城拼图流程图](puzzle-greatwall-流程图.md)

## 1. Steward 如何对应真实世界：是机器人 Agent 的部署态吗？

Ego 系统可以理解为机器人 Agent 在真实世界中的部署态；Steward 整体还包括围绕它的仿真、实验和评估设施。

按照现有设计，迁移到真实世界时，各部分对应如下：

| Steward 组件 | 仿真中 | 真实世界中 |
|---|---|---|
| 世界 | WSim 模拟的厨房、物体和机器人 | 实际房间、物体和机器人本体 |
| 传感器与执行器接口 HAL | 读取渲染图像、模拟编码器，执行仿真动作 | 连接相机、编码器、电机与机器人控制器 |
| ES：机器人对世界的认识 | 从仿真传感器重建 | 从真实传感器重建 |
| ESim：内部预测 | 根据 ES 预测动作后果 | 仍根据 ES 预测动作后果 |
| Ego Harness | 理解任务、编排技能、处理失败 | 继续承担这些职责 |
| World Harness / Observer | 构建场景、注入扰动、读取真值评估 | 转成实验编排和外部测量；完整真值通常无法取得 |

到了真实世界，外部 WSim 被现实替代，机器人内部的 ESim 仍然存在。机器人依然需要在动手之前，根据自己掌握的信息判断能不能拿到、会不会碰撞、放下后是否稳定。

### 1.1 部署时的三层职责

- **Ego Harness**：接收“收拾餐桌”这样的目标，拆解任务、调用工具、反思失败、复用能力。
- **Ego Runtime**：持续感知、维护 ES、规划运动、预测风险、执行技能和进行安全监督。
- **硬件适配与控制**：接入具体机器人的传感器、控制器和执行器。

这几层可以分布在机器人机载电脑和远端服务器上。需要实时响应的控制与安全机制应在本地运行，语言模型可以远程调用。

### 1.2 从仿真迁移到实机的条件

“换 HAL，上层不变”是 Steward 的架构目标，真正落地仍需要验证。真实机器人会带来标定偏差、通信延迟、抓取打滑、接触误差，以及仿真中未覆盖的故障。技能实现、物理参数和安全机制都可能需要适配；本次讨论所依据的项目进度中，实体机器人阶段还属于规划。

Ego 是被部署、持续行动和积累经验的机器人 Agent；Steward 仿真与观察平面是帮助它训练、复现失败和验证改进的实验设施。将来若打通“实机失败回传 → 仿真复现 → 改进技能或模型 → 验证后部署”，两部分就组成了完整的迭代闭环。

## 2. Ego 里面有 memory 吗？

有，但目前是几种分散的记忆机制，还不是统一的长期记忆系统。按本次阅读的代码，可以分成：

| 记忆 | 保存什么 | 保留范围 |
|---|---|---|
| 世界状态记忆 ES | 看见过的物体、位置、类别、不确定度、支撑与包含关系等 | Ego Runtime 运行期间持续维护 |
| 任务与反思记忆 | 当前指令、之前失败的步骤、反思内容 | 当前任务和会话；反思历史有长度限制 |
| 程序工作记忆 | `run_code` 定义的变量、辅助函数 | 同一个 Harness 进程内 |
| 长期能力记忆 | 已保存的技能程序、任务组合方法、参数说明、版本和使用结果 | 写入磁盘，跨会话、跨场景保留 |

### 2.1 ES：记住世界现在是什么样

ES 让机器人记住当前世界。例如，杯子进入关着的抽屉后，机器人不会因为暂时看不到就立即忘记它；机器人自己移动容器时，也会相应更新里面物体的位置。这属于持续维护的世界认知。

运行期间维护 ES 不等于重启后自动恢复 ES；不能仅凭这些状态维护机制推断它具备跨重启的环境记忆。

### 2.2 能力库：记住某类事情怎么做

Agent 可以把编写的程序保存成 `skill`，或者把多个技能组合成 `recipe`。后续任务通过 `capability_list` / `capability_get` 找回并执行；代码变化会形成新版本，使用结果会影响其状态。

文件保存在机器人自己的 `DSH_HOME/steward-capabilities/`。能力库允许知识以可执行程序的形式跨会话、跨场景保留。

当前能力库的成功统计包含“程序无错误结束”。因此，能力被标记为 `verified` 不等于已经确认物理任务达成，也不等于完成了实机或跨场景泛化验证。

### 2.3 尚未补齐的长期记忆

目前不能把它理解成机器人会自动记住所有经历，并在以后主动回忆。会话日志留存和长期记忆检索是两回事。从本次阅读的实现看，尚未形成完整机制，自动把“昨天在这个厨房发生过什么”“主人有什么偏好”“某种材质经常打滑”等经历提炼、保存，再按需召回。

对应真实机器人，它目前已有当前世界的记忆、当前任务的记忆，以及可持久积累的做事方法；跨天的生活经历、用户偏好和物理经验记忆，还有待补齐。

## 3. 两部分之间的逻辑关系

真实世界提供传感器观测 → Ego Runtime 将观测融合成 ES，维护当前世界认知 → ESim 根据 ES 预测行动后果 → Ego Harness 结合任务与反思历史选择下一步 → Runtime 执行技能并获得新观测 → 可复用的方法保存进能力库，供后续任务调用。

这条链已经连接了感知、状态记忆、预测、行动与能力积累。若要进一步实现跨天的持续学习，还需要补上经历提炼与检索、任务结果验证，以及物理知识和技能的持续修订。

## 5. 当前可选的 Phase 与例子

四个可选配置主要改变仿真器交给 Ego 的感知信息。用厨房里「把杯子放到餐桌上」这一任务对照，能看出每种配置把哪些判断交给机器人自己做。

| 配置 | 仿真器给什么，Ego 做什么 | 例子 | 适合验证什么 |
|---|---|---| --- |
| `phase0` 理想感知 | 从仿真真值生成带噪的类别、位姿和包围盒。Ego 融合多帧检测，维护 Ego-State 并规划动作。 | 机器人转头看到杯子，直接收到「这是杯子、在相机前方约一米」的检测，就可以规划过去拿。检测仍受视野和遮挡限制，关在抽屉里的杯子不会自动出现在检测结果里。 | 感知相对可靠时，任务理解、规划和动作能否跑通。 |
| `phase0-misnamed` 名称混淆 | 仍给出位置和尺寸，但按配置故意报错部分物体的类别，用于测试失败反思。 | 把指令改成「把拼图盒放到餐桌上」。仿真器把盒子报成 `picture`，Ego 按名称查找失败后，可以检查候选物体的尺寸和外观，判断它是否就是拼图盒。 | 物体名称与指令对不上时，Ego 能否检查证据并修正判断。 |
| `phase1` RGB-D 与仿真掩码 | 给 RGB、深度和匿名实例掩码。仿真器指出哪些像素属于同一个物体，Ego 自己估计三维几何、分类并融合多个视角。 | 仿真器圈出杯子的像素，但不提供类别。Ego 用深度还原三维点，按尺寸和形状判断它像不像杯子。如果只看到上半截，可以换个角度再估。 | 已知物体像素区域时，三维重建、分类和跟踪是否可靠。 |
| `phase1-sam` RGB-D 与 SAM 3.1 | 给 RGB 和深度。Ego 在关键帧调用 SAM 3.1 做实例分割，再做三维估计和融合。 | SAM 要先从整张图里找到杯子并圈出像素。如果杯子被餐盘挡住，SAM 可能漏检，Ego 可以移动相机重新观察。 | 分割出现漏检或误分类时，整条感知和任务链路能否继续工作。 |

拿「把杯子放到桌上」来对照，保持场景和指令一致：

- `phase0` 跑不通，可以先排查任务规划和动作执行。
- `phase0` 能跑而 `phase1` 失败，优先检查几何估计、分类或跟踪。
- `phase1` 能跑而 `phase1-sam` 失败，进一步看 SAM 有没有漏掉杯子，或者把杯子与背景分到了一起。

这些对照能缩小排查范围，具体原因还要看该次运行的观测和动作记录。

项目文档将 Phase 0 标为已完成、Phase 1 标为进行中，并记录了 SAM 3.1 的召回率仍低于仿真掩码。参见 [Phase 配置](../../steward/src/steward/phases.py)、[理想检测实现](../../steward/src/steward/world/sim.py)和[项目进度](../../steward.md#13-implementation-progress)。

## 6. 后续 Phase 的目标与例子

长城拼图案例的模块交互见 [puzzle-greatwall 时序图与流程图](puzzle-greatwall-流程图.md)。图册包含实际任务的六个环节、四种感知配置对照和 Phase 2–5 的路线图。

以下例子描述路线图上的目标。当前已有简化 ESim 做几何与风险检查，更完整的物理推演属于 Phase 2。

| 阶段 | 计划重点 | 例子 |
|---|---|---|
| Phase 2 | 物理推演、风险评估和可控扰动 | 放杯子前比较靠桌边放和往里放的风险。实验再在餐桌附近引入障碍，观察机器人能否发现变化、重新预测并改道。 |
| Phase 3 | 精细操作和长时任务 | 接到「准备早餐」后，机器人要开抽屉、取餐具、倒水和摆桌。发现杯子摆歪时，先调整杯子再继续倒水。 |
| Phase 4 | 多机器人协作与显式通信 | 一台机器人负责从柜子取杯子，另一台负责摆桌。前者报告「杯子已放在操作台」，后者用自己的相机确认后取走。 |
| Phase 5 | 硬件适配、标定和实机验证 | 将同一条「把杯子放到餐桌上」指令交给实体机器人。Ego 从真实相机和编码器获取观测，通过硬件接口控制底盘与夹爪，再检查杯子是否放稳。 |

## 7. Steward 的实际意义

### 7.1 能力复用

抓取、翻面、检查顶面和放置是工程师提供的通用工具。Ego 在猫拼图任务中把这些工具编排成可保存的程序。换到长城拼图后，它取回并复用按参考图拼装、图案匹配、摊开和翻面等程序，再把修改后的配方写回能力库。这让一次任务形成的做法可以用于下一次任务。长城那次有 9/12 条相邻关系满足条件，最大拼合组为 8/9 片，体现了复用的进展，也给后续调试留下了具体的结果。 [拼图运行记录](../../steward.md#13-implementation-progress)

### 7.2 仿真验证

可以让 Ego 在同一个长城场景、同一条指令下，分别使用理想感知、仿真掩码和 SAM 感知。如果理想感知下能找到并摆放拼片，换到 SAM 后漏掉一片，就可以优先检查分割是否漏检或把相邻拼片粘在一起。世界侧评估还可以用真值位姿独立核对相邻关系，帮助开发者区分感知错误、抓放偏差和配方错误。已有长城运行记录来自 `phase0`，其余配置是可用来验证的对照设计。 [长城拼图流程图](puzzle-greatwall-流程图.md)

### 7.3 真实部署

部署到实体机器人时，拼图配方可以继续通过 Ego 调用观察、抓取、翻面和放置，传感与执行则接入真实相机、编码器和机械臂。实机上需要验证相机和夹爪标定、拼片打滑以及实际落点误差。部署价值可以用同类任务衡量，例如换一套拼图或换一张桌子后，机器人能否复用已有做法、减少人工编程和接管，并通过观测确认最后的拼合结果。 [实机阶段路线图](../../steward.md#13-implementation-progress)
