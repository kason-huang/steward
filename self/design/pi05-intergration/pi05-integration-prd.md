# Steward π0.5 接入 PRD

日期：2026-11-05。状态：待技术核实与实现评审；尚未实现。本文根据本次讨论、Steward 设计说明和现有代码整理，不替代 `steward.md` 的约束。本次交付为本地设计文档，不发布 Issue。

技术方案及单阶段的实施与验收统一维护在[接入设计](pi05-integration-design.md)中；本文维护产品目标与需求范围。

## Problem Statement

Steward 已有世界仿真器 WSim、机器人自我运行时 ER、Ego-State（ES）、简化的 ESim、技能执行器，以及运行于 DeepSeek Harness 的 Ego Harness（EH）和 World Harness（WH）。用户希望在这套系统中引入 π0.5，让 EH 理解任务并编排操作，由 ER 使用相机图像、本体状态和操作目标驱动策略，最终在仿真场景中完成一次选定的完整任务。

当前底层技能针对 `steward_bot` 编写，由几何规则和显式控制过程生成靠近、对齐、升降、伸缩及夹爪开合动作。高层智能体负责选择目标与技能，尚未接入根据连续相机图像和本体反馈生成动作的学习型操作策略。因此，已有任务流程的成功不能作为 π0.5 操作能力的证据。

当前抓取采用理想附着：仿真器在夹爪闭合时按世界侧几何条件选取物体，使其刚性跟随夹爪，并关闭一般附着物体的碰撞；可倾倒容器保留碰撞。该机制省略了通过手指接触、夹持力和摩擦建立并维持抓持的过程，可以支持高层任务流程验证，但不足以验证策略对抓取偏差、滑移、掉落和携物碰撞的处理能力。本次需要在仿真中完成由策略驱动的物理接触抓取与放置，使这些物理结果能够真实发生并被记录。

现有 `steward_bot` 采用移动底盘、升降、伸缩和两轴手腕，其机构、控制指令与反馈不能假定兼容现成 π0.5 权重。当前世界侧资产编译与接触实现、机器人侧运动学与相机观测，以及感知、完成判定和安全预测也包含旧本体假设，不能自动覆盖新机械臂。仅连接推理服务或转换动作向量不足以解决这些差距，需要建立经过验证的权重、本体、控制器、传感器和任务组合。具体实现依据及待核实项见[差距分析](pi05-integration-gaps.md)。

用户需要一条从真实策略执行到高层任务编排的可验证路径，同时保留 Steward 的核心要求：不修改上游 Harness，机器人不能读取世界真值 GT，实时控制独立于 LLM，动作受到预测凭据和运行时安全监督约束。验收还必须区分“执行结束”“机器人认为目标完成”和“世界侧确认目标完成”。

## Solution

直接使用 π0.5，先在 Steward 内新增与所选权重匹配的机器人本体和最小 Scenario，保留现有 `steward_bot`。沿用现有 EH → `ctx.ego` → Ego API → ER 的调用链，把 π0.5 接到 ER 的技能执行侧。EH 提交操作目标与约束，ER 负责持续观测、策略推理、动作执行和结束判断。

新本体通过夹爪执行器和物理接触完成抓取、搬运与释放，物体运动由接触力、摩擦、重力和惯性共同决定。新路径不得通过理想附着、直接改写被抓物位姿或关闭被抓物碰撞来替代抓持，也不得在释放时人为清零速度。机器人通过可用的本体反馈与视觉估计持物和目标完成情况；世界侧独立记录实际物理结果。

统一接口指 EH 使用一致的技能预测、提交、状态查询与停止语义；不要求不同机器人共享相同的动作向量，也不把模型专用字段散布到 EH 的任务编排中。模型输入输出与本体控制之间的转换由 ER 的策略适配实现承担。

本次只有一个验收阶段：EH 提交一个受支持的完整任务，ER 在一个技能 Job 内运行 π0.5 直到任务结束。任务可以包含抓取、搬运和放置，策略执行期间允许反复观测与推理。机器人依据自身传感器与 ES 决策；世界侧独立使用 GT 验收，结果只提供给实验员、WH 与界面，不作为机器人继续执行的输入。

### 已确定的范围

- 直接接入 π0.5，不先用 ACT 过渡。
- 从没有现成策略、权重运行环境和配套仿真项目的起点搭建；用户有 Linux NVIDIA GPU 机器，具体配置后续补充。
- 首期允许新增匹配权重的机器人本体和最小场景，不要求直接控制 `steward_bot`。
- 新本体的抓取与放置采用仿真中的物理接触机制，允许发生抓空、滑移、掉落和碰撞；原有本体保留理想夹爪，两类结果分别标明。
- 首期限定选定基准任务的支持范围，不承诺任意自然语言任务。
- 完成一次选定的完整任务即可验收；真实策略执行是验收依据，测试替身用于验证接口与故障路径。
- 所有实现与设计受 `steward.md` 和现有 Steward 模块职责约束。

## User Stories

1. 作为实验员，我希望通过现有 EH 提交自然语言任务，以便继续使用 Steward 的机器人交互方式。
2. 作为实验员，我希望明确知道首期支持哪些操作，以便区分不支持的任务与策略执行失败。
3. 作为实验员，我希望新增机器人与所选权重的训练配置匹配，以便先验证策略执行而不混入未知的本体迁移问题。
4. 作为实验员，我希望保留原有 `steward_bot` 和场景，以便继续运行现有实验。
5. 作为实验员，我希望先看到一次真实 π0.5 完整任务执行，以便确认链路已经从工具调用贯通到物理效果。
6. 作为 EH 的使用者，我希望 EH 继续使用技能工具，以便无需了解策略服务协议和动作张量。
7. 作为 EH 的使用者，我希望每个执行动作先取得有效预测凭据，以便维持既有的风险评估流程。
8. 作为 EH 的使用者，我希望技能结果包含机器人侧的完成依据和失败原因，以便决定继续、重新观察或报告问题。
9. 作为 EH 的使用者，我希望机器人不确定是否完成时明确报告不确定，以便避免把推理结束误认为任务成功。
10. 作为操作员，我希望现有停止工具和急停入口能够中断策略执行，以便及时停止运动。
11. 作为操作员，我希望取消后排队的动作不会继续下发，以便停止请求具有实际效果。
12. 作为操作员，我希望推理服务断连、超时或返回无效动作时，ER 停止依赖该结果的动作并报告原因，以便识别执行状态是否可信。
13. 作为操作员，我希望能够查看当前技能和执行记录，以便区分等待推理、正在运动、执行结束和故障。
14. 作为实验员，我希望同时查看机器人自己的完成判断和世界侧的真实结果，以便发现误判。
15. 作为实验员，我希望 GT 判定不返回 EH 或 ER，以便保持实验的信息隔离。
16. 作为实验员，我希望可以检查关键传感器帧、动作记录和模型版本，以便分析失败原因。
17. 作为实验员，我希望能够在相同场景和初始条件下重复实验，以便比较策略和参数变更。
18. 作为实验员，我希望记录推理耗时和观测时间戳，以便识别陈旧观测对动作的影响。
19. 作为开发者，我希望模型输入输出的适配集中在 ER，以便将来替换权重或机器人时控制修改范围。
20. 作为开发者，我希望所有 DSH 依赖继续集中在 Steward 的适配工作区，以便保持实时运行时独立。
21. 作为开发者，我希望端点、模型选择、超时和执行限制通过配置给出，以便在用户的 GPU 机器上部署。
22. 作为维护者，我希望沿现有 Ego API、工具与真实 profile 测试，以便验证组合后的行为而不只验证适配函数。
23. 作为维护者，我希望旧机器人、技能和组合配置的相关检查继续通过，以便新增策略不会破坏现有功能。
24. 作为维护者，我希望明确记录当前 ESim 和安全监督对新策略能够检查的内容，以便不把简化检查宣传为完整的物理安全保证。
25. 作为实验员，我希望新本体通过物理夹爪接触完成抓取与放置，并保留抓空、滑移、掉落和碰撞等实际结果，以便验证策略的物理操作能力。

## Implementation Decisions

本节区分已确定的职责与本 PRD 提出的实施要求；具体权重、本体资产和接口字段尚未完成技术验证。

### 1. 延续 Steward 的进程与依赖划分

- EH 理解任务、制定计划、选择技能并处理异常；WH 布置世界、管理实验和读取评估结果。
- ER 持续维护 ES，调用 ESim，运行技能和安全监督。π0.5 推理属于技能执行侧，不作为 EH 的聊天模型提供者接入。
- WSim 推进世界物理并渲染传感器。LLM 和推理服务延迟不得决定物理循环的实现方式。
- 所选策略服务可部署在 GPU 机器上；ER 保持执行控制权，远程模型输出必须经过本地检查后才能成为执行器命令。
- 只在 Steward 自有目录实施，不修改上游包、主循环、会话格式、根工作区或上游检查脚本。DSH 依赖继续集中在适配工作区，Node 应用继续经命名 profile 启动。

### 2. 权重、本体和最小场景共同选型

- 优先复用已有 π0.5 专用权重及其配套机器人、观测和任务配置。OpenPI 的 `pi05_libero` 是当前候选，不是已验证的最终选择。
- 新增的本体、资产与 Scenario 必须纳入 Steward 的世界侧管理，复用既有传感器通道和执行器通道。独立跑通官方示例可以作为选型证据，不能代替 Steward 内的验收。
- 选型核对项包括机器人机构、夹爪、关节顺序、坐标系、相机位置与内参、图像预处理、状态归一化、动作含义及单位、动作序列长度和执行频率。
- 本体与场景必须保留任务所需的碰撞几何、惯性、夹爪接触和控制器行为。放入容器的任务必须使用具有实际开口和内部空间的碰撞几何，不能用实心碰撞体或位置标签代替容纳关系。
- 如候选配置需要扩展场景表示、WSim 控制或机器人侧估计器，修改应保持现有本体可用；不能把所有机器人强制转换为旧本体的升降与伸缩控制。
- 现成权重不适配时，先记录差距和成本，再调整本体或权重选择。本 PRD 不默认授权开展数据采集与模型训练项目。

### 3. 复用现有技能调用链和 Job

- 优先沿用 `ctx.ego` 的 Definition / Provider / Consumer，以及 `ego_predict`、`skill_run`、`skill_status` 和 `body_stop`。
- 当前实现通过 HTTP 连接 Ego API；设计说明中的 gRPC 是目标设计，接入 π0.5 不以传输协议迁移为前提。
- 当前 `skill_run` 默认等待，可选择立即返回 ER 技能 Job；状态、等待和停止继续由 ER 管理。不为本次接入默认启用 Ego bundle 已禁用的上游 `tool-jobs`、工作流、shell 或文件工具。
- 如现有技能词汇无法表达所选策略任务，只在 Steward 自有服务定义、提供者、工具和测试中显式扩展，并更新全部消费者。不得把一个不能独立执行的动作片段伪装为现有 `pick` 或 `place` 技能。
- EH 层的统一语义是目标、约束、预测凭据、技能状态与结果；策略选择和本体映射属于运行时配置。需要新增的字段和能力列表在选型核实后确定。

### 4. ER 管理完整的策略执行周期

- ER 从机器人传感器通道取得相机图像和本体观测，结合技能目标构造推理输入；禁止加入世界对象 ID、真实物体位姿、GT 成功标记或隐藏任务状态。
- 每次推理结果须绑定对应技能执行及观测时间；停止、执行结束或新的控制权归属生效后，迟到结果不得继续产生动作。
- 策略适配器负责输入预处理、输出解析、单位与坐标转换。ER 负责动作序列调度、观测刷新、执行限制、取消和资源释放。
- 对外部推理响应验证数值有限性、维度、动作范围与兼容性；不符合配置的响应失败并报告，不能静默截取、补零或改用其他策略掩盖故障。
- 复用现有独占控制与停止机制。断连、超时或执行状态未知时停止依赖该状态的工作；不要把“请求取消已发送”描述为“机器人已停止”。

### 5. 预测凭据必须覆盖实际执行

- 保留 EH 守卫和 ER 再次核验的双层结构，继续拒绝缺失、过期、已使用、不可行或超风险限制的凭据。
- 当前技能凭据对应显式计划；π0.5 会在执行中依据新观测产生动作。旧技能计划的凭据不能自动视为对任意新动作序列的批准。
- 本 PRD 要求定义凭据授权的技能目标、执行范围和有效条件，并在 ER 对实际将执行的动作实施检查。超出授权范围或状态变化使预测失效时，停止执行并请求重新预测。
- 具体采用动作序列预测、短时滚动检查或其他受限执行方式，需要结合新本体和 ESim 能力确定。不得先放开任意动作，再把安全检查作为后续工作。
- 现有 ESim 是简化实现，完整物理推演与部分安全机制仍属设计目标；本次必须明确实现能力与缺口。策略推理成功不能代替风险检查。

### 6. 完成判断与世界侧评估分离

- ER 的执行状态与目标是否达成应可区分。推理服务返回动作、动作序列执行完毕或达到步数上限，都不能单独作为目标成功依据。
- EH/ER 使用自身传感器、ES 和可观测的技能结束条件判断完成；无法确认时返回未确认及原因，具体结果字段在接口设计中确定。
- 实验员、WH 和世界侧评估使用 GT 独立核对实际目标，记录机器人判断与真实结果是否一致。评估输出不得进入 Ego API 返回值、EH 上下文、策略输入或恢复决策。
- 选定任务定义可检查的目标和机器人侧完成依据，禁止用隐藏的基准成功标记直接驱动技能结束或下一步选择。

### 7. 观测、日志与时间

- EH 继续以结构化 ES 和技能结果为主要输入，图像按需提供；连续策略图像不逐帧加入 LLM 上下文。
- 模型可见内容沿现有工具和会话记录机制保存。机器人侧传感器与动作记录、世界侧 GT 评估分开存储并保持访问隔离。
- 为新增策略保存模型和配置标识、观测时间、动作输出、执行结果与故障原因，能够关联到 Episode 和技能 Job；具体载体遵循现有 Recorder 演进，不把尚未实现的完整 MCAP 能力作为既有事实。
- 策略控制遵循现有仿真时钟与回路协调方式；GPU 推理期间如何等待、续租和处理过期观测需明确。部署参数经配置校验，不硬编码。
- 现有 Ego API 输入重放不包含新策略每次外部推理结果；不得直接宣称它足以重现 VLA 执行。重放新增路径需记录实际策略输出及应用时刻，不以重新调用模型代替确定的执行记录。

### 8. 失败处理延续现有职责

- 技能失败、策略故障和完成未确认均返回 EH；后续依赖操作不能因前一步仅“执行结束”就自动启动。
- EH 可依据自身日志、ES、预测问题和 blockers 重新观察或调整计划，无法解决时使用现有 `report_problem` 向操作员报告目标、步骤、诊断与证据。
- 现有家务脚本的清障、自救和活锁处理属于特定流程，不能假定新策略自动继承全部行为。也不把本次讨论中尚未选定的“失败立即等待”或“固定重试一次”写成全局规则。
- 本次不另行建设通用自动恢复框架；新路径必须有界结束、可取消，并明确何时停止依赖操作和报告问题。

## Testing Decisions

测试以可观察行为为准，优先使用已有的最高层接口。主要测试位置是现有 Ego API、`ctx.ego` 工具与守卫、真实 ego profile、WSim 机器人端口，以及世界侧 Episode 验收。新增策略通信只作为 ER 的适配测试点，不建立第二套绕过技能系统的产品入口。

### 已有测试依据

- Steward 的 Ego 测试已验证 ES 局部性、无泄漏和 ESim 风险判断。
- 端到端测试已通过 Ego API 执行杯子搬运，并在测试侧读取世界状态验收，适合作为“机器人执行、世界侧核对”的先例。
- DSH 工具测试已有 `ctx.ego` 替身、默认等待、凭据拒绝与问题报告覆盖；真实组合测试和配置快照用于检查 profile 的实际工具集合。
- 时钟与倍率测试已验证现有技能的记录重放，新策略需要扩展记录内容后再验证对应承诺。
- 相机、Phase、停止告警和独占控制已有相关测试，可作为新本体回归的依据。

### 接口与故障验证

1. 经 Ego API 提交一个受支持技能，验证预测、执行、查询、等待和结束状态，覆盖默认等待与非等待调用。
2. 经真实工具与守卫路径验证无凭据、凭据过期或已使用、风险过高时拒绝运动；不得只调用内部函数证明守卫有效。
3. 使用可控的策略服务替身，验证超时、断连、错误维度、非有限数、动作越界、迟到响应和旧观测的处理。断言没有不应下发的执行器命令，并保留可诊断失败结果。
4. 验证执行中的停止、服务卸载和控制权冲突：旧动作不得继续下发，资源按约定释放；若停止未确认，结果明确标记未知状态。
5. 验证实际动作超出预测授权条件时被拒绝，不能只证明开始时存在一个 receipt。
6. 验证策略输入、Ego 工具结果和模型上下文不包含 GT、世界对象 ID 或基准成功标记；机器人端口仍无法访问 WCA。
7. 验证机器人判断成功但世界侧失败时，两份结论均被保留，世界侧结论不反馈机器人控制路径。
8. 验证所选本体的相机、关节、坐标和动作映射与配置一致；缺少必要配置时在加载或最早可核实阶段失败。
9. 使用真实 profile 检查新增能力的模型可见输出与会话记录，并保留通用计算机工具的禁用策略。

### 单阶段：完整任务验收

- 在新增的匹配本体与最小 Scenario 中，由 EH 经现有技能工具链发起一次受支持操作，真实调用 π0.5，实际驱动 WSim。
- 抓取、搬运和释放由物理夹爪接触完成；保留被抓物碰撞与自由动力学。补充抓空或偏位、夹持不足及携物接触障碍的场景，核对不会自动附着、刚性跟随或穿过障碍；对实际发生的滑移、掉落和失败保留记录。
- 放置任务核对松开后的物理运动与实际承托；放入容器时核对物体经开口进入内部并由容器承托。夹爪闭合命令或仿真隐藏附着标记不能充当机器人侧抓取成功的证据。
- 保存该任务的机器人侧完成判断、世界侧目标核对、预测与执行记录及可检查的图像或录像证据。同一 Episode 中 Job 为 `succeeded`、机器人目标结论为 `achieved`、世界侧确认目标达成，且无信息泄漏和安全绕过，才算完成完整任务链路验收。
- 另外覆盖一次执行中取消与一次推理故障，验证动作终止行为和可诊断结果。
- 正常成功路径不能通过测试替身、脚本策略、理想吸附或直接设置物体位姿替代。

### 重复性与回归

固定并记录场景、种子、模型版本、归一化配置、动作应用时刻及结束条件。首期以一次完整任务成功贯通为验收目标，保存全部尝试及失败记录；取消与故障另行验证。批量成功率评测和跨任务泛化留待后续，单次成功只证明该任务链路贯通。

实现时运行受影响的 Steward Python 测试、DSH 适配包编译与测试、组合配置检查和真实 GPU 仿真冒烟。按修改范围补充现有本体及场景回归，不默认运行整个上游测试套件。本 PRD 编写本身不代表这些实现检查已运行。

## Out of Scope

- EH 将任务拆成多个独立策略技能并编排依赖操作，以及跨技能末态衔接验证。

- ACT 过渡方案及其他策略模型的实现。
- 首期让现成 π0.5 权重直接控制原有 `steward_bot`。
- 任意自然语言目标、任意机器人、任意场景的泛化保证。
- 修改上游 Harness、主循环、持久化格式或根工作区。
- 绕过 `ctx.ego`、预测凭据、ER 安全检查或信息隔离来演示模型。
- 让 EH 或 π0.5 读取 GT、评估器结论或未观测的世界状态。
- 将基准运行器直接接到 Harness 后，宣称已完成 Steward 内的机器人接入。
- 为本次接入整体替换现有 WSim、ES、感知系统、Ego API 传输协议或技能 Job 机制。
- 完整通用 ESim 物理预测、全场景安全证明、多机器人、真实硬件部署和模型训练工程。
- 独立的新 UI 产品、跨进程崩溃后自动续执行，以及通用自动恢复框架。

## Further Notes

### 实施前需核实的事实

以下是工程核实项，不是重新访谈已经确定的产品目标。若核实结果要求改变已确定范围，再提交具体取舍。

| 核实项 | 必须形成的结果 |
|---|---|
| GPU 环境 | 用户补充显卡、显存、系统与访问方式后，确认推理和渲染能运行；不得假定当前 Mac 承担 GPU 执行 |
| 权重与本体 | 固定候选版本、模型配置、本体资产、相机与动作定义，给出独立运行证据和 Steward 适配差距 |
| 本体支持 | 核实场景转换、WSim、RobotLink、估计器与 ESim 中针对旧本体的假设，列出必要扩展 |
| 物理抓取与放置 | 验证夹爪接触、稳定搬运、自然释放和容器承托，以及抓空、滑移、掉落与碰撞等结果；明确旧理想夹爪与新路径的区别 |
| 选定任务 | 固定一条权重支持的完整任务指令及初态，明确机器人侧与世界侧的完成条件 |
| 安全覆盖 | 定义凭据授权范围、滚动动作检查、停止确认与超时行为，说明简化 ESim 的能力限制 |
| 时钟与重放 | 明确推理等待期间的仿真时钟协调，定义策略输出及动作时刻的记录与重放方式 |
| 基线与验收 | 核实选定任务可执行，冻结场景、种子与执行限制，保存一次完整任务成功及取消、故障证据 |

建议实施顺序：核实权重与本体及独立基线 → 将最小机器人场景纳入 Steward 并贯通传感器与执行器 → 接入 ER 策略执行、安全检查和记录 → 完成一次完整任务验收。独立基线用于选型，Steward 内的完整链路用于产品验收。
